> **Audience Note:** This document specifies the observable behaviors, data contracts, prompt templates, and operational rules of the Image Generation and World State systems. It is written for non-programmer system analysts and AI reasoning agents. It deliberately contains zero code snippets, function names, file paths, or programming abstractions.

# 1. Image Generation System

## Purpose
The Image Generation system creates visual artwork depicting scenes from the interactive roleplay narrative using an external image rendering backend (ComfyUI). It exists to:
1. Automatically illustrate key story moments directly inside the chat dialogue (inline images) or as message attachments (gallery images).
2. Allow manual on-demand rendering of scenes or character portraits based on recent dialogue.
3. Enforce strict visual continuity across long-running stories so that characters retain consistent physical characteristics (hair color, eye shape, race, build) while dynamically wearing the clothing appropriate to the current scene and setting.

### When Generation Happens & What Triggers It
Image generation occurs through five distinct triggers:
1. **Automatic Story-Driven Trigger (Inline/New Message):** When the AI story model generates a narrative reply, the extension inspects the text for image command tags. If an image tag is found, the extension extracts the prompt, replaces the raw tag with an in-chat visual placeholder ("`[Generating Image...]`"), and sends the rendering request to the image backend.
2. **Manual Scene Generation (Settings Panel):** The user clicks the manual generation button in the Image Generation settings panel. The system gathers recent chat messages, evaluates active scene attire and character tags, asks an AI model to compose an optimized image prompt, and sends it to the image backend.
3. **Manual Custom Prompt Generation:** The user writes their own custom prompt text into an input box in the settings panel and submits it directly.
4. **Inline Image Regeneration (In-Chat Retry):** Every rendered inline image in chat possesses an overlay retry button. Tapping this button restores the in-chat loading placeholder and re-submits the exact prompt used for that image with a new random seed.
5. **Gallery Overswipe Regeneration:** If an image is stored in the message gallery, swiping right past the last image triggers an automatic regeneration of that image with a fresh seed.

## Image Generation Settings

Every configuration option available to the user is documented below, including its human-readable label, purpose, default value, options, and behavioral effects.

### General & Connection Settings

#### 1. Enable Image Generation
* **What it controls:** Master switch for all image generation features.
* **Default value:** Disabled (`false`).
* **Options:** Enabled / Disabled.
* **Behavior:** When disabled, image tags generated by the story model are ignored, retry buttons are deactivated, the quick-generation launcher button is hidden, and no background requests are sent to the image backend. When enabled, all automated and manual workflows become active.
* **Scope:** Affects all future turns and immediately toggles the visibility of the quick-launch UI button.

#### 2. ComfyUI Server Address
* **What it controls:** The network address (URL) of the running image generation backend.
* **Default value:** `http://127.0.0.1:8188`
* **Options:** Any valid HTTP URL (e.g. `http://localhost:8188`, or a remote tunnel address).
* **Behavior:** Used for all API requests to the backend (connection test, model list retrieval, sampler list retrieval, queuing generation workflows, image downloads, and WebSocket progress streaming).
* **Interactions:** The "Test Connection" button tests this address and immediately queries the server for installed models, LoRAs, and resolution presets.

#### 3. Image Insertion Mode
* **What it controls:** How generated images are placed into the chat interface.
* **Default value:** `Inline (Inside Text)`
* **Options:**
  * `Inline (Inside Text)`: Replaces image tags inside the character's reply with interactive HTML card blocks right at the exact position in the prose where the tag appeared.
  * `Gallery (Attached to Message)`: Attaches the image as a SillyTavern message attachment/gallery image, visible in the character's message header.
  * `Separate Message`: Appends a dedicated new chat message containing the generated artwork.
* **Scope:** Affects all future image generations.

#### 4. Workflow Template
* **What it controls:** Selects which ComfyUI workflow JSON graph is used to generate images.
* **Default value:** First available workflow returned by the backend (or blank if unpopulated).
* **Options:** Populated dynamically from saved workflow files in SillyTavern's backend.
* **Behavior:** The extension loads the chosen workflow template and performs placeholder substitution (inserting positive prompt, negative prompt, seed, sampler, steps, CFG, denoise, dimensions, and LoRA parameters) into the corresponding graph nodes before submission.

### Generation Parameters & Prompt Controls

#### 5. Trigger Mode
* **What it controls:** The condition under which the story-writing AI is told to generate images during normal story replies.
* **Default value:** `Always`
* **Options:**
  * `Always`: Every AI turn instructs the story model to generate an image tag for the scene.
  * `Frequency`: The AI is only instructed to generate an image once every *N* replies (configured by **Auto-Generation Frequency**).
  * `Conditional (Story Actions Only)`: The AI is instructed to output an image tag *only* if a character in the scene is explicitly taking a photograph, sending a picture, or sharing an image. If no photo action occurs, the model is strictly told not to emit image tags.
* **Interactions:** In `Frequency` mode, an internal counter checks total assistant messages; if `(count + 1) % Frequency == 0`, the instruction is injected.

#### 6. Auto-Generation Frequency
* **What it controls:** In `Frequency` trigger mode, specifies the reply interval between image generations.
* **Default value:** `1` (every reply).
* **Options:** Integer from `1` upwards.

#### 7. Image Count per Response
* **What it controls:** How many images the story AI is instructed to generate in a single turn.
* **Default value:** `1`
* **Options:** `1`, `2`, `3`, `4`, `5`.
* **Behavior:** Adjusts the prompt instruction (e.g. "insert 2 of this image tag") and staggers the resulting backend generation jobs by 1.5 seconds each to avoid overloading the image rendering hardware.

#### 8. Prompt Architecture & Perspective Template
* **What it controls:** The structural rules and examples fed to the AI prompt engineer model when composing the image prompt.
* **Default value:** `Illustrious/Anima + Cinematic`
* **Options:**
  1. `Illustrious/Anima + Cinematic`: Booru-tag based, third-person cinematic camera angles, multi-character sentence separation.
  2. `Z Image (SDXL) + Cinematic`: Natural language complete sentences, cinematic camera distance/angle instructions, cinematic lighting tags.
  3. `Illustrious/Anima + POV`: Booru-tag based, strict first-person point-of-view, viewer hands/anchors, forbidden from describing user's face.
  4. `Z Image (SDXL) + POV`: Natural language sentences, first-person perspective, foreground environmental anchors or user hands.
  5. `Illustrious/Anima + Portrait`: Booru-tag based, single-character focus, upper body or face crop, simple studio background.
  6. `Z Image (SDXL) + Portrait`: Natural language single-character detailed portrait, studio lighting, simple non-distracting background.

#### 9. Include Prompting Examples
* **What it controls:** Appends high-quality concrete example image prompts to the prompt engineer instructions.
* **Default value:** Enabled (`true`).
* **Options:** Enabled / Disabled.
* **Behavior:** When enabled, increases input tokens but substantially improves adherence to tag formatting and anti-character-bleeding rules.

#### 10. Better Booru Tags / Direct Language
* **What it controls:** Injects strict explicit dictionary directives into the prompt generator.
* **Default value:** Disabled (`false`).
* **Options:** Enabled / Disabled.
* **Behavior:** When enabled, forces the model to use raw uncensored Booru tags instead of natural language euphemisms (e.g. enforces "naked" instead of "wearing nothing", "erection" instead of "visible arousal") and provides an anatomical tag lookup table for explicit scenes.

#### 11. Inject Character Appearance & Continuity Tags
* **What it controls:** Master switch for whether saved character appearance traits are automatically evaluated and sent to the prompt generator.
* **Default value:** Disabled (`false`).
* **Options:** Enabled / Disabled.
* **Behavior:** When disabled, only the active scene environment and attire from World State are injected; character-specific physical traits (hair, eyes, skin, build) are omitted. When enabled, characters relevant to the ongoing dialogue have their static appearance tags merged into the prompt context.

#### 12. Extra Prompt Instructions
* **What it controls:** Global free-form instructions appended to every prompt generation request.
* **Default value:** Empty string (`""`).
* **Behavior:** Useful for enforcing custom visual flavors across all images (e.g. "moody dark atmosphere, volumetric fog, oil painting texture").

#### 13. Positive Prompt Prefix
* **What it controls:** Raw text prepended directly to the front of every prompt before submitting to the image rendering backend.
* **Default value:** Empty string (`""`).
* **Behavior:** Useful for base model quality boosters (e.g. "`score_9, score_8_up, masterpiece,`").

#### 14. Negative Prompt Override
* **What it controls:** Negative prompt text injected into the workflow graph.
* **Default value:** `bad quality, blurry, worst quality, low quality`
* **Behavior:** Replaces the `%negative_prompt%` placeholder in the workflow.

#### 15. Checkpoint Model & Sampler
* **What they control:** Selects the model checkpoint file and sampling algorithm sent to the backend.
* **Default values:** Model: empty / first available; Sampler: `euler`.

#### 16. Sampling Parameters (Steps, CFG, Denoise, CLIP Skip)
* **Steps:** Integer slider `1` to `100` (Default: `20`).
* **CFG Scale:** Float slider `1.0` to `30.0` (Default: `7.0`).
* **Denoise:** Float slider `0.0` to `1.0` (Default: `0.5`).
* **CLIP Skip:** Integer slider `1` to `12` (Default: `1`, converted to negative value `-1` for SDXL/Illustrious standards).

#### 17. Resolution Presets & Custom Dimensions
* **What it controls:** Width and Height in pixels.
* **Default value:** `1024 x 1024` (SDXL 1:1 square).
* **Presets available:**
  * SDXL Square: `1024 x 1024`
  * SDXL Landscape: `1152 x 896`, `1216 x 832`, `1344 x 768`
  * SDXL Portrait: `896 x 1152`, `832 x 1216`, `768 x 1344`
  * SD 1.5 Square: `512 x 512`
  * SD 1.5 Landscape: `768 x 512`
  * SD 1.5 Portrait: `512 x 768`
* **Custom inputs:** Allows arbitrary pixel values.

#### 18. Seed
* **What it controls:** Generation randomness seed.
* **Default value:** `-1` (Random).
* **Behavior:** If set to `-1`, a cryptographically random integer between `0` and `1,000,000,000` is generated on every run. If set to a specific positive number, that exact seed is submitted.

#### 19. LoRA Lab (Slots 1 to 4)
* **What it controls:** Four independent LoRA slots. Each slot configures:
  * LoRA filename (selected from ComfyUI).
  * LoRA weight multiplier (Float slider `0.0` to `2.0`, Default: `1.0`).
  * Trigger words (Text string).
* **Behavior:** The selected LoRA filename and weight are substituted into the workflow graph placeholders (`%lora1%` to `%lora4%`, `%lorawt1%` to `%lorawt4%`). If trigger words are specified, they are automatically prefixed to the positive prompt.

#### 20. Preview Image Prompt
* **What it controls:** Intercepts generation with an interactive popup before queuing to the backend.
* **Default value:** Disabled (`false`).
* **Behavior:** When enabled, an interactive modal dialog displays the complete assembled prompt. The user can review, edit, or append tags in real-time, then click "Send to ComfyUI" or "Cancel".

#### 21. Compress Images
* **What it controls:** Compression format of images saved to disk.
* **Default value:** Enabled (`true`).
* **Behavior:** When enabled, raw PNG images from the backend are converted to JPEG at 90% quality via browser canvas, significantly reducing chat file sizes and loading lag. When disabled, images are saved as lossless PNGs.

### Character Appearance & Continuity Subsystem

Located directly inside the Image Generation tab, this subsystem stores persistent physical descriptions of characters and tracks active scene attire.

#### 22. Active Scene Snapshot Box
* **What it displays:** A live status dashboard reflecting the current scene from the World State ledger:
  * Location (e.g. "Royal Library | Capital")
  * Atmosphere/Weather (e.g. "Heavy Rain, Dim Candlelight")
  * Player Character (PC) current outfit.
* **Behavior:** Automatically updates whenever a World State block or update is processed in the chat. Displays "(No active scene on record)" if the chat has not yet generated a World State.

#### 23. Character Appearance Cards List
Each registered character is displayed in an individual card containing:
* **Character Name:** The canonical identity of the character.
* **Provisional Tag:** Highlighted badge indicating whether the entry was automatically scanned from card lore or hand-crafted by the user.
* **Lock / Unlock Button:**
  * `Unlocked` (Default for scanned entries): The character's tags can be refined or overwritten if a re-scan is performed.
  * `Locked`: The entry is protected; re-scanning the character sheet will never alter or overwrite these tags.
* **Delete Button:** Permanently removes the character from the Appearance list.
* **Live Attire Badge:**
  * `👗 Attire (current scene): [Clothing Description]` (Green): Shown when the character is currently present in the active World State scene.
  * `(Not in active scene)` (Muted Grey): Shown when the character is absent or off-screen.
* **Aliases Input Field:** A comma-separated list of nicknames or alternate names (e.g. `Matt, Matty, Little Brother`). Allows narrative nicknames in story dialogue to match the canonical character.
* **Physical Traits Textarea:** Booru-style visual tags defining immutable physical characteristics (e.g. `1girl, mature female, pale skin, emerald eyes, waist-length black hair, high ponytail, athletic build`).

#### 24. "Scan Character Sheet" Button
* **What it does:** Reads the active character card's description lore, isolates character sheets, and sends them via an isolated background prompt to extract all named characters and their visual Booru tags.
* **Behavior:**
  * Bypasses chat history completely (only card lore is sent).
  * Automatically parses structured nicknames (e.g. `Matthew "Matt"` becomes canonical name `Matthew` with alias `Matt`).
  * Merges new characters into the list.
  * Respects `Locked` cards: locked cards are skipped and preserved, while unlocked cards have their visual tags refreshed.
* **Scope & Isolation:** Character Appearance tags are saved directly into the individual chat file metadata. They **never** leak across chat switches, even when "Sync Tab Globally" is active.

# 2. Exact Image Prompt Behavior

The extension uses two distinct prompt generation layers:
1. **The In-Chat Directives (`[[img1]]`):** Tells the primary roleplay model to insert `<img prompt="...">` tags in its narrative reply.
2. **The Prompt Engineer Query (`___PS_IMAGE_GEN___`):** Dedicated prompt sent to an AI model to compose an optimized image prompt from scratch (used during manual generation or background workflows).

## Exact Text: The In-Chat Story Directive Template
When the story model generates a reply, the following instruction block is injected into the roleplay prompt (via `[[img1]]`):

```text
### IMAGE GENERATION:
{{conditionalText}}Within your response, insert {{imageCount}} of this image tag: <img prompt="[prompt]"> to illustrate the scene. Adhere strictly to any visual tags and active attire/environment provided below to maintain visual continuity.
{{templateRules}}

{{promptExtra}}

{{directLanguage}}

{{npcImageTags}}

{{templateExamples}}
```

### Exact Replacements for Template Slots:
* **`{{conditionalText}}`**:
  * In `Always` or `Frequency` mode: Empty string (`""`).
  * In `Conditional` mode:
    ```text
    CRITICAL INSTRUCTION: ONLY output the <img prompt="..."> tag if the character is explicitly taking a photo, sending a picture, or sharing an image in this exact moment. If not, do NOT output the image tags at all.
    ```
* **`{{imageCount}}`**: The configured number of images (`1` to `5`).
* **`{{promptExtra}}`**: If configured, `Extra Instructions: [User text]`.
* **`{{directLanguage}}`**: If enabled, injects:
  ```text
  **DIRECT LANGUAGE:** Use exact Booru tags only. "naked" not "wearing nothing." "erection" not "visible arousal."

  **NSFW TAG REFERENCE (use when scene is explicit):**
  Body: naked, nude, topless, exposed nipples, small breasts, medium breasts, large breasts, spread legs, ass, erection, veins, veiny penis
  Actions: hetero, sex, vaginal, anal, oral, fellatio, after fellatio, paizuri, straddling, riding, missionary, doggystyle, cowgirl position, moaning, open mouth, tongue out, ahegao, clenching teeth
  Fluids: cum, cum on body, cum on breasts, cum on face, cum on hair, cum on tongue, cum in mouth, cum inside, ejaculation, facial, saliva, sweat
  State: flushed face, heavy breathing, trembling, crying with eyes open, half-closed eyes, solo focus
  ```
* **`{{npcImageTags}}`**: The assembled Visual Continuity Context (see Section 3).

* Requires simple, non-distracting background tags (`simple background, gradient background, dark background, blurred background`) and studio lighting tags (`soft lighting, studio lighting, natural lighting`).
* Explicitly forbids complex backgrounds and multiple characters.

# 3. Image Generation Context

The prompt pipeline enforces a strict **Two-Tier Visual Continuity Model**:

```
┌────────────────────────────────────────────────────────┐
│             VISUAL CONTINUITY PIPELINE                 │
├────────────────────────────────────────────────────────┤
│ TIER 1: Static Physical Traits (Permanent Lore)       │
│ Source: Character Appearance Tags (Image Gen Tab)      │
│ Scope: Species, age, skin, hair color/style, eye shape │
│ Scored by: Keyword relevance to recent dialogue        │
├────────────────────────────────────────────────────────┤
│ TIER 2: Semi-Sticky Scene Baseline (World State)       │
│ Source: Live World State Ledger                        │
│ Scope: Active Location, Atmosphere/Weather, Attire     │
│ Authority: Mandatory baseline for current scene        │
└────────────────────────────────────────────────────────┘
```

### Breakdown of Context Elements:

1. **Static Character Physical Traits (Tier 1):**
   * **Included when:** The character is mentioned in the active dialogue or matches recent keywords, and `Inject Character Appearance & Continuity Tags` is enabled.
   * **Format:**
     ```text
     **RELEVANT NPC IMAGE TAGS:**
     [Matthew]: 1boy, mature male, short brown hair, emerald green eyes, light beard, tall athletic build
     [Aqua]: 1girl, young woman, long blue hair, blue eyes, goddess
     ```
   * **Omitted when:** The toggle is disabled, or no character tags match the recent conversation.

2. **Active Scene Attire & Environment (Tier 2):**
   * **Included when:** An active World State exists in the chat.
   * **Format:**
     ```text
     **ACTIVE SCENE ATTIRE & ENVIRONMENT (MANDATORY BASELINE):**
     • Location: Grand Library Archive | Royal Palace
     • Weather/Atmosphere: Thunderstorm outside, warm flickering candlelight
     • Kazuma (PC) Outfit: Dark travel cloak over linen tunic, leather boots
     • Matthew Outfit: Cropped black band shirt, pleated skirt
     • Aqua Outfit: Blue divine dress with gold trim
     *Adhere strictly to this clothing and setting. Do not change attire or location unless the prose explicitly depicts it changing.*
     ```
   * **Precedence Rule:** If a character's static tags describe default clothes (e.g. "school uniform") but the World State tracks an active outfit (e.g. "pajamas"), the model is instructed to adhere strictly to the **World State Active Scene Attire**. Physical traits (hair, eyes, skin) come from Tier 1; clothing comes from Tier 2.

3. **Context Deliberately Excluded:**
   * Character thoughts, internal agendas, secrets, and relationship bond levels are **never** sent to the image model.
   * Off-screen characters and unresolved narrative quest threads are **excluded** from image prompts.
   * The user's face and facial features are strictly forbidden in first-person POV templates.

# 4. World State System

## Purpose
The World State system maintains an authoritative, live, compiled record of the physical scene environment, time progression, character physical states, and narrative tracking.

Large language models frequently suffer from "continuity drift" over extended roleplay sessions—forgetting that it is nighttime, changing clothing between rooms, or resurrecting items dropped several turns ago. The World State ledger provides an anchor that ensures the AI adheres to existing physical reality until events in the story explicitly change it.

---

## World State Information Schema

The live ledger tracks the following properties:

| Property | Type / Format | Description & Purpose | Default / Empty State |
|---|---|---|---|
| `dateTime` | String | Current in-universe date, day of week, and time of day. | `""` (Empty string) |
| `location` | String | Primary setting, room, region, or landmark. | `""` (Empty string) |
| `weather` | String | Environmental atmosphere, weather, temperature, and lighting. | `""` (Empty string) |
| `pc.name` | String | Name of the Player Character. | `""` (Falls back to user persona) |
| `pc.outfit` | String | Current garments, accessories, and state of dress of the PC. | `""` |
| `pc.position` | String | Physical posture and spatial placement (e.g. "leaning against the tavern counter"). | `""` |
| `pc.condition` | String | Observable physical condition (injuries, exhaustion, intoxication). | `""` |
| `pc.carrying` | String | Items actively held in hands, pockets, or bags. | `""` |
| `npcOutfits` | Map (`[name]: outfit`) | Normalized mapping of active outfits for all NPCs present in the scene. | `{}` (Empty map) |
| `npcs` | String | Full markdown details for present NPCs (Outfits, Postures, Visible Moods, Agendas, Secrets). | `""` |
| `threads` | String | Active narrative tension, uncompleted tasks, planted seeds, consequence timers, and arc/scene phases. | `""` |
| `rawText` | String | Full verbatim markdown representation of the compiled World State block. | `""` |
| `history` | Array | Rolling chronological list of previous ledger states tied to message turns. | `[]` (Empty array) |

## World State Lifecycle

```
[Start of Chat / Turn 1]
         │
         ▼
[No World State Exists] ──► Inject Full <World_State> Template into Prompt
                                            │
                                            ▼
                               [Model Emits <World_State>]
                                            │
                                            ▼
                           [Bootstrap Ledger Initialized]
                           - Normalize names at the door
                           - Seed live ledger & history[0]
                           - Render full scene board card
                                            │
   ┌────────────────────────────────────────┘
   │
   ▼
[Turn 2+: Baseline Exists]
   │
   ├──► 1. Inject Active Baseline into Prompt ([[infoblockcurrent]])
   │       "The <World_State> above is your active baseline."
   │
   ├──► 2. Inject Delta Template ([[infoblock]])
   │       "Output <World_Update> ONLY if something changed."
   │
   ▼
[Model Emits <World_Update> Delta (or omits if unchanged)]
   │
   ├──► Parse Changed Fields (Header, PC, NPCs, Arrivals, Departures)
   ├──► Normalize Names against Active Cast & Aliases
   ├──► Update Live Ledger In-Place
   ├──► Apply Delta Edits Directly to Verbatim rawText
   ├──► Append to Rollback History
   └──► Transform in-chat card to display full updated scene board
```

### Detailed Lifecycle Phases:

1. **Bootstrap Phase (Turn 1):**
   * When `hasWorldState()` is false, the prompt engine injects the full `<World_State>` blueprint.
   * When the AI model replies, the parser extracts the `<World_State>` block.
   * `setWorldStateBootstrap()` stores the initial state, normalizes NPC names, and creates the first history checkpoint at `msgIndex`.
2. **Delta Update Phase (Turn 2 onwards):**
   * The prompt engine injects the existing compiled World State into the prompt using the `[[infoblockcurrent]]` slot so the AI model has full awareness of the baseline.
   * In the instructions slot `[[infoblock]]`, the engine sends the `<World_Update>` delta template, strictly commanding the model *not* to re-emit the entire state, but only lines that changed.
   * When the AI model replies, the parser searches for `<World_Update>`. If found, `applyWorldStateUpdate()` mutates the active ledger, updates `rawText`, records the diff, and appends a new state to `history`.
3. **Unchanged Turns:**
   * If a scene continues without clothing, location, or character changes, the model omits the `<World_Update>` tag completely. The extension detects no updates, keeps the existing ledger active, and automatically renders the existing scene board card on the message.
4. **Chat Rewind & Swipe Rollback:**
   * When a user swipes an AI message or deletes messages, the `worldStateRollbackHistoryFrom(index)` lifecycle hook triggers.
   * Any history checkpoints at or past the rewound index are deleted.
   * The ledger state is immediately restored to the newest surviving history entry before that index.
   * If the user deletes all messages back to the bootstrap message, the World State resets to `null`, re-enabling bootstrap mode for the next turn.

```text
**🧍 {{user}}:** (Include only if {{user}} changed outfit, position, or status)

* *Position:* [New posture or action]
* *Mood:* [Shifted emotional state]
* *Agenda:* [Shifted goal]
* *Secret:* [Revealed or new secret]

**📡 Off-Screen:** (Add or update if characters leave or are tracked elsewhere)

**🔥 Unresolved Threads:** (Update if threads change)

**⏳ Consequence Timers:** [New or expired timer]

```

## Compact Mode Template
If the user enables **Compact Mode** in settings, intermediate turns omit deep lore, off-screen characters, and threads to conserve prompt tokens:

```text
Omit deep lore, unresolved threads, and off-screen tracking. Focus ONLY on immediate physical presence:
<World_State>
**Time & Loc:** [Time] at [Location]
**PC:** [Brief visible clothing] | [Current posture/position]
**NPCs Present:**
* [Name]: [Brief visible clothing] | [Posture/position]
</World_State>
```
* **Full State Interval:** Every *N* replies (configured by `Full state every X replies`, default: `5`), the system temporarily deactivates compact mode and requests the full comprehensive state to keep narrative tracking up to date.

# 6. World State → Image Generation

The interaction between World State and Image Generation represents the core continuity engine of the suite.

```
┌────────────────────────────────────────────────────────┐
│                   WORLD STATE LEDGER                   │
│                                                        │
│  Location: "Ancient Cathedral Ruins | Sunken Valley"   │
│  Weather:  "Heavy morning fog, god rays through roof"  │
│  PC Outfit: "Reinforced plate armor, tattered cape"   │
│  NPC Outfits:                                          │
│    - Matthew: "Casual blue hoodie, dark jeans"        │
│    - Aqua:    "Ceremonial silk dress, gold hairpins"   │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
          [Extraction & Name Normalization]
      (Resolves narrative nicknames: "Matt" ➔ "Matthew")
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│           IMAGE GEN VISUAL CONTINUITY BLOCK            │
│                                                        │
│  **ACTIVE SCENE ATTIRE & ENVIRONMENT (MANDATORY)**     │
│  • Location: Ancient Cathedral Ruins | Sunken Valley   │
│  • Weather/Atmosphere: Heavy morning fog, god rays...  │
│  • Player (PC) Outfit: Reinforced plate armor...       │
│  • Matthew Outfit: Casual blue hoodie, dark jeans      │
│  • Aqua Outfit: Ceremonial silk dress, gold hairpins   │
│                                                        │
│  Merged with Character Appearance Static Tags:         │
│  [Matthew]: 1boy, short brown hair, green eyes...      │
│  [Aqua]: 1girl, long blue hair, blue eyes, goddess...  │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│              FINAL ASSEMBLED IMAGE PROMPT              │
│                                                        │
│  "masterpiece, best quality, cinematic composition,    │
│   wide shot, 2girls, 1boy, The young man on the left   │
│   is Matthew with short brown hair and green eyes,     │
│   wearing a casual blue hoodie and dark jeans..."      │
└────────────────────────────────────────────────────────┘
```

### Specific Operational Rules:
1. **Values that affect images:**
   * `location` ➔ Sets background environment tags.
   * `weather` ➔ Sets lighting, atmosphere, rain/fog, and particle tags.
   * `pc.outfit` ➔ Strictly sets the clothing of the player character.
   * `npcOutfits` ➔ Strictly sets the clothing of every present NPC.
2. **Values that DO NOT affect images:**
   * `dateTime` (Time of day only influences the image if reflected in `weather` lighting).
   * `pc.condition` (Injuries or exhaustion are not forced unless prominent in recent dialogue).
   * `pc.carrying` (Items are generally left to recent prose actions).
   * `mood`, `agenda`, `secret` (Internal psychological states do not dictate image generation).
   * `offscreen` (Characters tracked off-screen are explicitly suppressed from the image).
   * `threads`, `seeds`, `timers`, `arcPhase`, `scenePhase` (Have zero impact on images).
3. **Conflict Resolution:**
   * If a character's static card lore says "Always wears formal black suit", but the World State ledger currently records `Outfit: Wet bathing suit`, the **World State ledger strictly wins**.
   * If the recent prose depicts a character stripping off a coat, the AI model generates an outfit update in `<World_Update>`. The ledger updates on turn completion, and subsequent image generations immediately reflect the new attire.

# 8. Edge Cases and Failure Behavior

### 1. Character Name Variations ("Matt" vs "Matthew")
* **Situation:** Story dialogue or World State refers to a character as "Matt", but the Character Appearance list registers him as "Matthew".
* **Behavior:** The central name matcher applies a 4-step deterministic ladder:
  1. Exact case-insensitive comparison (`"matthew" === "matthew"`).
  2. Explicit Aliases lookup (checks if "Matt" is listed in Matthew's `Aliases` field).
  3. Token & Honorific stripping (e.g. `"Lady Darkness"` matches `"Darkness"`, `"Aqua (Goddess)"` matches `"Aqua"`).
  4. Unambiguous prefix matching (if length $\ge 3$ and `"Matthew".startsWith("Matt")`).
* **Uniqueness Guard:** If multiple cast members share a prefix (e.g. both "Samantha" and "Samuel" exist when "Sam" is used), automatic prefix matching declines to guess and returns `null`. An explicit alias in the UI is required.

### 2. Missing or Broken World State Block
* **Situation:** The model fails to emit `<World_Update>` or emits an unparseable block.
* **Behavior:** The system declines to update the ledger. It falls back to the existing live ledger without crashing, logs a diagnostic notice, and preserves the previous turn's state.

### 3. Stale Character Outfit Removal
* **Situation:** An NPC leaves the scene (e.g. `- Matt` in delta update), but the ledger stored their outfit under `Matthew`.
* **Behavior:** The system checks exact key deletion first. If absent, it checks if exactly one stored outfit key matches via the name matcher. If unique, it deletes the outfit from the active scene without leaving a "ghost" outfit behind. If multiple outfits match ambiguously, deletion is safely aborted.

### 4. Backend (ComfyUI) Disconnection or Timeout
* **Situation:** The user enables Image Generation, but ComfyUI is not running or the workstation runs out of VRAM.
* **Behavior:**
  * In-chat inline mode: The visual placeholder updates to:
    `[Image Generation Failed: Failed to fetch]`
  * An invisible retry anchor is attached inside the placeholder HTML.
  * When the user restarts ComfyUI, they can hover over the error placeholder and tap the retry icon to re-render without editing the message.

### 5. Chat Switch During Background Generation
* **Situation:** The user generates an image in Chat A, but immediately switches to Chat B while ComfyUI is still rendering.
* **Behavior:** When the image download completes, the extension verifies the active chat ID and message ID. If the active chat has changed, the write operation is safely declined, preventing the image from corrupting or overwriting an unrelated message in Chat B.

# 10. Design Intent and Important Constraints

### 1. "Zero Prompt Template Redesign" Rule
The extension machinery must bridge gaps between user lore, story prose, and image generation **without modifying author-designed engine prompt templates**. Name normalization, nickname splitting, and attire matching are handled programmatically at the boundaries rather than by forcing the story LLM to change its literary phrasing.

### 2. Separation of Physical Traits vs. Scene Attire
Static traits (hair color, eye shape, species, body dimensions) are intentionally separated from clothing and location. Physical traits belong in Character Appearance cards; clothing and location belong in the live World State ledger. This prevents clothing changes from destroying a character's physical definition.

### 3. Strict Chat Isolation for Character Appearance Tags
Character appearance tags are stored inside the individual chat metadata, not in the global extension configuration. This ensures that opening a different chat with an alternate version of a character (or an entirely different roleplay universe) never contaminates or overwrites character visual tags.

### 4. Uniqueness Guards over Aggressive Fuzzy Matching
The system deliberately refuses to use arbitrary Levenshtein fuzzy string distance for character names. In roleplay casts with multiple similar names (e.g. "Sara" and "Sarah", or "Samantha" and "Samuel"), fuzzy guessing creates false identity merges. If a match is ambiguous, the system requires an explicit alias.

# 11. Known Problems & Architectural Quirks

### 1. Hyphenated Japanese Honorifics Matching Quirk
* **Observation:** The honorific stripping rule currently strips space-separated titles and suffixes (e.g. `"Lady Darkness"` ➔ `"Darkness"`, `"Aqua sama"` ➔ `"Aqua"`), but does not automatically strip hyphen-joined suffixes (e.g. `"Aqua-sama"`).
* **Workaround / Mitigating Behavior:** In practice, the prefix matching ladder (`"Aqua-sama".startsWith("Aqua")`) rescues this match in almost all single-character scenarios unless another character named "Aqua-something" exists in the same cast.

### 2. Live Tab Snapshot Staleness
* **Observation:** The "Active Scene Snapshot" box inside the Image Generation settings tab renders when the tab is opened. If the user leaves the tab open on a second monitor while continuing a chat, the snapshot box does not update live until the tab is re-clicked or re-rendered.

### 3. Missing Chat Metadata in Unsupported Environments
* **Observation:** If the extension is run in a minimal headless or test environment where SillyTavern's `chat_metadata` API is unavailable, character appearance tags remain held in session memory and will not persist across browser restarts.
