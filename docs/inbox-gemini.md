### Edge cases to pin in the plan

**E1 — Name drift (the one that will actually bite).** Three independent free-text name sources: `characterTags` keys (user-typed or model-extracted), `npcOutfits` keys (whatever the ledger model writes), and the sheet-extracted names. The live-attire badge does `ws.npcOutfits[name]` — a case difference ("megumin" vs "Megumin") or a drifted ledger name ("Megumin (Kazama)") silently misses and shows "(Not in active scene)" forever, and the user has no idea why. Pin in the plan: badge lookup is **case-insensitive exact match** (trim + casefold on both sides); state explicitly that anything beyond that (fuzzy/contains matching) is a v2 idea. Same rule should apply wherever the scanner dedupes on save.

**E2 — Rescan semantics vs 001's locked/provisional contract (plan-contract).** 001 says `locked: true` = "auto-extraction will never overwrite." A rescan violates that silently unless the plan says otherwise. Pin: rescan **creates** new names as `provisional: true`, **refreshes** `provisional` entries (that's their job), **skips** `locked` entries (toast how many were skipped). Also decide: if the sheet names a character identical to the user's persona name (party cards sometimes describe the PC), skip it or allow it? My call: allow (same face, harmless), say so in the plan.

**E3 — Extraction format.** Follow the established "EXACTLY this format" + dedicated parser pattern (injection.js:107 for NPC dossiers, `meguminFindNpcDossiers` in the data layer). The plan must state the literal output shape (I suggest: one section per character, name line + comma-separated Booru-style appearance tags only — no personality, no bonds, per Kazuma's no-dossiers rule) and where the parser lives. Instruct the model: *only characters explicitly named in the sheet* (hallucination is the failure mode; the user's safety net is the existing delete button, say that in the UI copy).

**E4 — What text to send.** Recommend extract-with-fallback: pull the `<character_sheet>` block out of `card.description` (case-insensitive, tolerant of a missing/mismatched closing tag), fall back to the full description if no match. Plan should state the fallback rule in one sentence and pick the cap/limit policy if any.

**E5 — Group chats & no-card state.** With a group selected, the "active card" is ambiguous (`characterId` may not mean what the user thinks), and with no character at all the index can be stale/-1. Guard like the NPC scan's (that one: `chatText.length < 100` → "Not enough chat history"). Suggested scope for v1: button scans the active *character* card; if a group is selected, either warn "scan covers one card — switch to a single character" or mark groups out of scope. **E6 — Live-UI staleness (Proposal 1).** The Image Gen settings tab renders once; the snapshot header and attire badges will go stale the moment the World State changes while the tab sits open. Same class as 001's gold-notice observation. Two options: (a) accept it and label the header (e.g. timestamp/"as of last render") — cheap, v1-appropriate; (b) subscribe to the generation-complete event and re-render the panel only while the tab is visible — better UX, more moving parts. My recommendation: (a) for 002, note (b) as a possible follow-up. The data is never wrong on a re-render; the only lie is "live" in the name — so maybe call it "Scene Snapshot" instead of "Live Scene" to keep the honesty budget balanced.
